# Meetings that connect everywhere: TURN in the stack, LiveKit in the all-in-one image

## Why

Two gaps keep meetings from working out of the box. Behind strict firewalls and symmetric NATs — most corporate
networks — a browser cannot reach LiveKit's media ports and the call never connects; the deployment guide says
"configure LiveKit's TURN (not automated here)". And the all-in-one image, the first thing a new customer runs,
has no LiveKit at all, so the product's headline feature is off in the first minute.

## What Changes

- **TURN in the Compose stack**: LiveKit's built-in TURN server is configured by the stack — over TLS on a port of
  the public host (through the reverse proxy's certificate) and over UDP — with the settings generated by
  `make init` and documented for a public install.
- **LiveKit in the all-in-one image**: the image runs LiveKit beside the server and Redis under supervisord, with a
  key and secret generated on first start and kept in the data volume; meetings are on by default. It needs two
  more published ports (7881/tcp and 7882/udp) and the host's address (`LIVEKIT_NODE_IP`) for other machines.
- A `meethub meetings check` command reports whether LiveKit is reachable, which addresses it advertises and
  whether TURN answers, so a wrong network setting is found before the first call.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `build-and-deploy`: TURN in the Compose stack, LiveKit in the all-in-one image.
- `server-cli`: the meetings check command.

## Impact

- `deployments/compose/compose.yml`, `Makefile` (`init`), `Dockerfile` (the `allinone` target copies the LiveKit
  server binary from its image pinned by digest), `docker/allinone/` (supervisord program, entrypoint generating
  the key and secret), the smoke test, `docs/deployment.md`.
- The all-in-one image grows by the LiveKit binary (tens of MiB) and exposes three more ports.
- No change to the server's meeting code besides the command.
