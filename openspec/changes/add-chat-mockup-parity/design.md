# Design

## Context

See proposal.md for the motivation. What shapes the approach:

- The chat of `add-chat-realtime` is in place: `internal/chat` (channel lock and revision, posts, history by cursor,
  audience queries), `internal/realtime` (hub, bus), the `chat` Pinia store and the components under
  `frontend/src/components/chat`. The shell is one file, `frontend/src/layouts/AppLayout.vue`, with a navigation rail.
- Three databases (SQLite, MariaDB, PostgreSQL) with one migration file per dialect; several replicas behind one
  Redis; a strict CSP (`img-src 'self' data: blob:`); a 1 MiB default request body limit.
- Mattermost v12.0.2 is the functional base (pins, search, profile images, favorites exist there); its AGPL server code
  is reference only.
- The approved layout is study A of `base/layouts/meethub-layouts.figcraft` (generated by `base/layouts/gen.py`, which
  fails when a text pair is below 7:1). The file is private source material and is never committed.

## Goals / Non-Goals

**Goals:**

- The chat screens match study A at 1280 px and above, and keep working on phones and at the QHD/4K zoom steps.
- One set of corner radii for every theme; AAA for the three MeetHub themes without touching the other palettes.
- Pins, search, pictures and favorites behave the same on the three databases and across replicas.

**Non-Goals:**

- The meeting room, the "Start meeting" button, the meeting card and upcoming meetings (`add-livekit-meetings`); the
  Files button and recent files (`add-file-uploads`). Their places in study A stay empty until then.
- Ranked or stemmed full-text search; searching archived channels; a storage abstraction for files.
- Bringing the 19 inherited themes to AAA.

## Decisions

### D1. Layout: team rail, navigation in the sidebar

`AppLayout.vue` keeps its four grid columns (64, 264, fluid, 320). The rail's content changes from sections to teams
(a `TeamRail` component fed by the store's `teams`, which already carry `has_unread` and `mention_count`); the section
links move to the top of the sidebar and Settings, the quick theme switcher and the user to its foot. `ChatSidebar`
keeps the team switcher: with the rail it is redundant on desktop but is the only switcher inside the phone drawer
header, and removing it would break muscle memory from Mattermost.

On phones the bottom bar keeps the section links (unchanged markup, new source list) and the drawer gains the team
tiles. *Alternative considered:* a second rail for sections (Teams style, study C) — rejected with the study.

### D2. Corner radii and AAA

Three tokens in the contract defaults of `style.css` — `--radius-sm: 4px`, `--radius-md: 6px`, `--radius-lg: 8px` —
used by the shared classes (`.btn`, `.inp`, `.pnl`, toasts, dialogs, popovers, chat items). Themes do not declare
them, and the theme lockstep test fails a theme file that does. Presence dots, counters and meeting pictures stay
round. The existing "0 px radius" contract test is replaced by one that reads the computed radius of the gallery's
controls and containers in every theme.

AAA: the contrast test's matrix gains a level per theme (`AAA` for `meethub-dark`, `meethub-light`, `high-contrast`,
`AA` for the rest), so the same recipes are measured against 7:1 or 4.5:1. `meethub-dark` takes the palette of the
spec; primary buttons use `#3d41cf` (white text 7.35:1) and links and mentions use the lighter accent text
`#b3b8ff`, because no single indigo reaches 7:1 both as a fill under white and as text on navy. `meethub-light` is
derived the same way (primary fill `#3d41cf`, text and muted text darkened until the recipes pass);
`high-contrast` is measured and adjusted only where it fails. The 22 gallery screenshots are regenerated.

*Alternative considered:* AAA for all 22 themes — rejected by the user: Matrix, Winamp and Pink Panther would lose
their look.

### D3. Schema (migration 00003, three dialects)

- `posts`: `pinned_at BIGINT NOT NULL DEFAULT 0`, `pinned_by` (26 chars, nullable); index `(channel_id, pinned_at)`
  to list pins newest first (rows with `pinned_at = 0` are skipped by the query's `pinned_at > 0`).
- `channel_members`: `favorite BOOLEAN NOT NULL DEFAULT FALSE`.
- `users`: `last_picture_update BIGINT NOT NULL DEFAULT 0`.
- `user_images`: `user_id` (primary key, foreign key to users), `data` (BLOB/BYTEA/LONGBLOB), `updated_at`.

Down steps drop them. No backfill is needed.

### D4. Pins

`chat.Service.Pin/Unpin` run under the channel lock of design D3 of the chat (lock order unchanged), bump the
channel revision, stamp the post's `revision`, `pinned_at`, `pinned_by`, and emit `post_edited` — the event
Mattermost sends for a pin — so the store's revision rule already handles duplicates and late events. `PostView`
gains `is_pinned`, `pinned_by`, `pinned_at` (the last two are MeetHub extensions: Mattermost does not say who
pinned, the mockup does). Soft delete clears the pin in the same statement that writes the tombstone. `edit_at` is
not touched, so a pinned message is not shown as edited.

### D5. Search: portable matching first

`POST /posts/search` parses `terms` into words, quoted phrases, `from:` and `in:` (Mattermost's modifiers) and runs
one query: posts joined to the caller's `channel_members` (so the scope is enforced by the join, not by a list of
ids), `delete_at = 0`, channel not archived, and `LOWER(message) LIKE ?` per term with `%`, `_` and the escape
character escaped, ordered by `(create_at, id)` descending with `LIMIT per_page + 1`. The rate limit reuses
`ratelimit.NewWindow` (10 per 10 s, key by user).

This is the same code on the three databases and has the same semantics everywhere (substring, case-insensitive
through `LOWER`). Its cost is a scan of the caller's channels' posts: fine at the scale budget for interactive use
because the join narrows the rows and the limit stops early, but not indexed.

*Alternative considered:* native full-text (PostgreSQL `tsvector`, MariaDB `FULLTEXT`, SQLite FTS5). It is faster
on large histories but gives three tokenizers with different stop words, minimum token lengths and accent rules, a
trigger-maintained table on SQLite and three test matrices. It can replace the query later behind the same service
method without changing the API; the code carries a `shortcut:` comment naming that upgrade.

### D6. Profile pictures in the database

Pictures live in `user_images`, not in the data directory: replicas share the database but not a disk, backups
already cover it, and the file storage abstraction belongs to `add-file-uploads`. At 256 px a PNG is tens of
kilobytes, so the table stays small.

Upload path: the route raises the body limit to 5 MiB plus the multipart overhead; the handler sniffs the format
from the bytes, reads the header with `image.DecodeConfig` and rejects more than 4096 px on a side before decoding,
decodes with the standard library (PNG, JPEG, first frame of a GIF), crops the centered square, scales to 256 px with
a box filter (each output pixel averages the source pixels it covers: a few lines, so no `golang.org/x/image`
dependency) and encodes PNG — re-encoding is what drops EXIF and any trailing payload. The
row and `users.last_picture_update` change in one transaction, then `user_updated` goes to the audience that
`chat.StatusWatchers` already computes for presence (the same "may see" rule).

Serving: `GET /users/{id}/image` checks visibility with the directory's predicate (404 otherwise), answers
`image/png`, `nosniff`, `Cache-Control: private, max-age=86400` and an ETag of `last_picture_update`; the SPA
requests `…/image?v=<last_picture_update>`, so a new picture is a new URL. The CSP already allows `img-src 'self'`.

*Alternative considered:* files under `app.data_dir` — simpler to serve, but wrong with more than one replica.
*Alternative considered:* generated default pictures on the server (Mattermost does) — initials rendered by the
client already exist and need no request.

### D7. Favorites

`channel_members.favorite`, set by `PUT /users/me/channels/{id}/favorite`, returned in the channel and conversation
lists, and announced to the caller's other connections with `preferences_changed` carrying
`{category: "favorite_channel", name: <channel id>, value: "true"|"false"}` — Mattermost's preference shape.
Deviation: Mattermost now models the sidebar as user-defined categories; MeetHub has one fixed category, so a flag
is enough and a later "categories" change can migrate it.

### D8. History around a message

`History` gains `around` and `after`: `around` loads `per_page / 2` rows on each side of the post's
`(create_at, id)` with the two existing index directions and returns both cursors; `after` pages forward with the
same opaque cursor encoding. Deleted messages inside the window come as tombstones, as in the history.

### D9. Frontend

- **Side panel**: one state, `details | thread | search`, in the chat store; closing a thread or the search returns
  to `details`. New components: `TeamRail`, `ChannelDetails`, `SearchPanel`, `PinnedBanner`, `ChannelMenu`,
  `QuickThemes`, `UserPicture` (picture with initials fallback, used by `MessageItem`, the sidebar, details and the
  shell's foot).
- **Jump mode**: jumping loads a window with `around` and marks the timeline as *detached*: `posted` events update
  counters but are not appended (the window is not contiguous with the present); scrolling down pages with `after`
  until the newest page, which re-attaches it. "Jump to recent" reloads the first page.
- **Browser state**: collapsed sections and the dismissed pin (`channel id → pinned_at`) in `localStorage`, read
  defensively; they are per-browser conveniences, not preferences.
- **Composer toolbar**: pure text transforms on the selection (wrap, prefix lines), unit-tested; no new dependency.
- **Dates**: `Intl.DateTimeFormat` with the app language for "Today, Jan 21".

### D10. Mattermost parity

| MeetHub (`/api/v1`) | Mattermost v4 | Deviation |
| --- | --- | --- |
| `POST /posts/{id}/pin`, `/unpin` | same paths | answers the post instead of a status object |
| `GET /channels/{id}/pinned` | same path | cursor paging |
| `POST /posts/search` | `POST /posts/search` | substring matching (D5); `{posts, has_more, channels}` instead of a post list with `order` |
| `POST/GET/DELETE /users/…/image` | same resource | `me` for writes; 404 instead of a default image |
| `PUT /users/me/channels/{id}/favorite` | sidebar categories | one fixed category (D7) |
| `GET /channels/{id}/posts?around=` | `before`/`after` post ids | opaque cursors, as the existing history |

Events `post_edited`, `user_updated` and `preferences_changed` keep Mattermost's names and payload keys.

### D11. Direction for meetings

Recorded for `add-livekit-meetings`, not built here: the room opens full screen (study D): video grid, round
controls centered at the bottom, the channel's messages in a floating panel on the right. The channel header's
"Start meeting" button and the details panel's room card are added by that change in the places study A reserves.

## Risks / Trade-offs

- [Search scans grow with history] → the join and the limit bound it, the rate limit caps abuse, and D5 names the
  indexed replacement; `make test-load` gains a search step to watch the latency.
- [A hostile image exhausts memory] → header check before decoding, 5 MiB body limit, one decode at a time per
  request, table-driven tests with a bomb and a polyglot file.
- [Pictures leak who exists] → the same 404 for "no picture" and "not visible", tested for guests.
- [The layout change breaks every e2e that clicks the rail] → the shell tasks update those suites in the same group.
- [Radius and palette change every screenshot] → baselines are regenerated once, in the visual-contract group, before
  any other UI work, so later diffs are meaningful.
- [Detached timeline misses live events] → counters still update, and re-attaching reloads through the API.

## Migration Plan

Migration `00003` is additive; the server applies it at start as usual. Rollback: `meethub migrate down` drops the
new columns and `user_images` (pins, favorites and pictures are lost; messages are not touched). Users see the new
radii and palette on the first load after the upgrade; saved theme ids do not change.
