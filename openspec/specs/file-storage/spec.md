# file-storage Specification

## Purpose
Defines where the bytes of uploaded files live: the storage drivers an installation chooses between, how they are
configured, and what keeps files available to every replica.

## Requirements

### Requirement: Storage drivers
File bytes SHALL be kept by one driver chosen by `files.driver`: `local` (the default), a directory that defaults to
`<data_dir>/files`, or `s3`, a bucket of an S3-compatible service. The database SHALL hold only the files'
metadata and their storage keys, never their bytes.

#### Scenario: Default installation
- **WHEN** MeetHub starts without any `files` setting
- **THEN** uploads are written under `<data_dir>/files` and can be downloaded after a restart

#### Scenario: Two replicas on S3
- **GIVEN** two replicas configured with the same bucket
- **WHEN** a file is uploaded through one and downloaded through the other
- **THEN** the download returns the same bytes

### Requirement: Storage keys
Every stored object SHALL have a key generated by the server from ids and a date (never from the file's name or any
other client text), so a name cannot place a file outside the storage root or over another file.

#### Scenario: Hostile file name
- **WHEN** a member uploads a file named `../../etc/passwd`
- **THEN** the object is stored under a generated key inside the storage root and the name is kept only as metadata

### Requirement: Storage availability
The readiness check SHALL report the storage (directory writable, or bucket reachable); while it is unavailable,
uploads and downloads SHALL answer `503` and the rest of the chat SHALL keep working.

#### Scenario: Bucket unreachable
- **GIVEN** the S3 service is down
- **WHEN** a member posts a text message and then tries to upload a file
- **THEN** the message is posted, the upload answers `503`, and `/api/v1/ready` reports the storage check as failed
